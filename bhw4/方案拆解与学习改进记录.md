## 2. 先明确我们解决的问题

### 2.1 三件容易混在一起的事

| 层次 | 当前定义 | 当前实验是否验证 |
|---|---|---|
| 原文相同 | 查询字符串与历史字符串完全相等 | 是，100 个 Exact 查询及摘要碰撞测试 |
| 向量相关 | 同一个 Embedding 模型下，余弦相似度不小于 0.80 | 是，300 个非重复查询 |
| 历史答案可直接复用 | 历史答案能正确回答当前问题 | 否，没有历史答案与人工复用标注 |

高 Recall 表示 LSH 很少遗漏“这个模型按阈值认定的邻居”，不等于回答正确率高。同意图、向量相似、答案可复用也不能自动画等号。例如询问最近 ATM 的距离，与询问最近 ATM 是否在两英里以内，可能语义相关，却需要不同形式的回答。

当前系统实现的是语义复用系统中的**检索环节**。检索成功后怎样选择历史答案、是否还需检查用户条件，是后续系统设计的问题。

### 2.2 统一记号

| 记号 | 含义 | 当前设置或说明 |
|---|---|---|
| N | 历史文本数量 | 10,003 |
| d | 向量维度 | 384 |
| q、u | 查询原文、归一化查询向量 | u 由公开模型生成 |
| x_i、v_i | 第 i 条历史原文、归一化向量 | 历史顺序固定 |
| τ | 判断相关的余弦阈值 | 0.80 |
| G(q) | 暴力搜索得到的真实相关 ID 集合 | `{i: u·v_i ≥ τ}` |
| C(q) | LSH 产生并去重的候选 ID 集合 | 其中可能包含大量无关项 |
| A(q) | 语义路径最终返回的 ID 集合 | `C(q) ∩ G(q)` |
| k | 每张表的 Hash bit 数 | 主配置 12 |
| L | 独立 Hash Table 数量 | 主配置 46 |

G 只用于离线评价。实际语义查询先生成 C，再精筛为 A，不允许先扫描全库算出 G，再伪装成 LSH 找到了结果。

Exact 命中的返回约定是“返回原文相等的 ID”。它可以提前结束，但不承诺同时返回所有其他语义邻居。因此 Exact 与 Semantic 两组查询分开评价。

## 3. 数据和向量是怎样准备的

### 3.1 数据流

```text
BANKING77 train.csv
  → 按原始字符串精确去重
  → 固定随机顺序
  → 10,003 条历史文本

BANKING77 test.csv
  → 去掉与历史原文完全重叠的文本
  → 精确去重
  → 固定随机抽取 300 条非重复查询

历史文本
  → 另取 100 条原文，测试 Exact 快速路径
```

抽样种子是 20261022。没有先看 G 是否非空再挑查询，所以最终自然出现了 27 个没有阈值邻居的查询。数据集有 77 个意图类别，但类别标签没有参与 Hash、LSH、参数选择或 Ground Truth。

### 3.2 从文本到向量

使用 `sentence-transformers/all-MiniLM-L6-v2` 的官方 ONNX AVX2 uint8 量化导出，在 CPU 上推理。每段文本最多 256 tokens，对有效 token 的输出作均值池化，再 L2 归一化，最终保存为 384 维 float32 向量。

量化描述的是模型推理使用的权重形式；保存的检索向量仍然是 float32。归一化后向量长度为 1，余弦公式中的两个范数变成 1，因此可以直接用点积计算相似度。

所有检索方法共用同一批向量。这让主实验主要比较搜索算法，而不是把不同模型、不同向量精度混在一起比较。当前没有验证量化模型与原始浮点模型的检索质量差异。

对应代码：[prepare.py](验证/prepare.py) 的 `prepare()` 负责下载与划分，`encode()` 负责分词、推理、池化、归一化与缓存。

**学习检查：**如果把模型替换掉，但仍固定 τ=0.80，相关集合 G 是否一定不变？为什么更换模型后不能直接沿用旧 Recall 作为同一任务的比较？

## 4. Exact Hash 这一层为什么存在

当前结构是：

```text
SHA256(UTF8(原始文本)) → 一组历史 ID
```

查询时先计算摘要，定位 ID 列表，再逐项核对原文。即使两个不同字符串产生相同摘要，也不会因为摘要相同就错误返回。审计程序通过“让所有文本返回同一个摘要”的方式验证了这一点。

普通 Hash 的目标是让键均匀分散，减少定位之后需要处理的碰撞。它不会因为两条文本语义相近，就主动让它们更容易碰撞。SHA-256 本身也不理解文本语义。

这层的价值在于：完全重复问题无需生成向量，也无需查 LSH。计算摘要仍有 O(|q|) 的字符处理成本，不能把从输入字符串到结果的全部工作都写成严格 O(1)。哈希表定位的期望成本通常是 O(1)，原文核验另计。

SHA-256 是当前实现的一个选择，不是题目要求的唯一选择。后续可以与直接使用原始字符串作为 Python 字典键比较；后者同样会进行键的相等性检查。是否更省时间与空间，需要在相同文本和碰撞处理语义下测量。

对应代码：[experiment.py](验证/experiment.py) 的 `ExactHash` 和 `reuse()` 的第一段。

## 5. LSH 是怎样改变搜索范围的

### 5.1 一个 Hash bit

随机选择方向向量 `r ~ N(0, I_d)`，定义：

\[
h_r(v)=\mathbf{1}[r\cdot v\geq 0].
\]

超平面 `r·v=0` 把空间分为两侧；bit 表示向量位于哪一侧。两个方向相近的向量更容易在同侧。若夹角为 θ，同侧概率为：

\[
p=1-\frac{\theta}{\pi},\qquad
p(s)=1-\frac{\arccos(s)}{\pi}.
\]

一个 bit 只能分成两个桶，候选通常太多。需要组合多个独立 bit。

### 5.2 一张表用 k 位做 AND

每个向量得到一个 k 位编号，例如 `101…011`。只有全部 k 位相同才同桶，碰撞概率变为：

\[
P_{\mathrm{table}}(s)=p(s)^k.
\]

增大 k 会让条件更严格，近点和远点的同桶概率都会下降。因此“加长 Hash 就能同时解决所有问题”不成立。

### 5.3 L 张表做 OR

用不同独立超平面建立 L 张表，只要在其中任意一张表同桶，就进入候选。全部 L 张表都没有相遇的概率是 `(1-p^k)^L`，因此：

\[
P(s)=1-\left(1-p(s)^k\right)^L.
\]

L 越大，相似项有更多进入候选的机会，无关项同样如此。表数还会增加超平面计算和存储。

### 5.4 候选必须去重、精筛

同一个历史 ID 可能同时出现在多张表的桶里；合并后只保留一次，再计算真实余弦。对语义路径来说：

\[
A(q)=\{i\in C(q):u\cdot v_i\geq\tau\}=C(q)\cap G(q).
\]

所以相对于这一定义的 G，最终输出没有低于阈值的误报，但可能漏掉从未进入 C 的相关项。精筛无法挽救候选生成阶段已经遗漏的元素。

这里没有候选上限，也没有全库回退；极端情况下所有向量同桶，候选仍可能达到 N。当前实现的近似性来自随机候选覆盖，不能声称每次查询都必然低于线性扫描成本。

## 6. 为什么主参数是 k=12、L=46

### 6.1 先定目标，再解约束

当前目标是在相似度边界 `s1=0.80` 处取得至少 95% 的单元素进入概率，并让 `s≤s0=0.20` 的低相似度元素进入概率不超过 5%。τ、95%、s0、5% 都是本次实验预先设定的设计选择。

对固定 k，近点约束给出最小整数表数：

\[
L(k)=\left\lceil
\frac{\ln(0.05)}{\ln(1-p(0.80)^k)}
\right\rceil.
\]

由于分母为负数，推导不等式时需要注意方向变化。对整数 k 依次检查远点约束，首个满足要求的组合是：

| k | L(k) | P(0.80) | P(0.20) | 是否同时满足 |
|---:|---:|---:|---:|---|
| 11 | 36 | 95.10% | 6.42% | 否 |
| 12 | 46 | 95.20% | 4.67% | 是，作为主配置 |
| 13 | 58 | 95.14% | 3.34% | 是，但需要更多表 |

对应代码：[experiment.py](验证/experiment.py) 的 `probability()` 与 `parameter_design()`。

### 6.2 这项推导的边界

95.20% 是对一对给定向量、随机生成索引而言的概率。它不是“每个查询都保证 95.20% Recall”，也不是“一次查询的所有邻居以 95.20% 概率全部被找到”。不同邻居的进入事件可能相关，不能随意将它们当作相互独立事件相乘。

实测平均 Recall 高于 95.20% 也不矛盾：许多真实邻居的相似度高于 0.80，其进入概率也更高。

远点概率 4.67% 不能直接当作候选比例的上限。真实库中还存在大量 `0.20<s<0.80` 的文本，它们更容易碰撞；近邻也会占用候选。因而实测平均候选比例 7.90% 并不推翻这个概率公式。

选最小可行 k 是一个容易解释的策略，但**没有证明它使实际延迟最小**。若后续以速度或内存为目标，应把投影、桶访问、去重、精筛和存储一起纳入目标函数，而不只比较 k 的大小。

**学习检查：**固定 L 增大 k，与“增大 k 后重新计算满足 95% 召回约束的 L”，为什么是两种不同的实验？

## 7. 从理论结构对应到当前代码

| 环节 | 代码位置 | 核心实现 | 需要观察的代价 |
|---|---|---|---|
| 精确匹配 | `ExactHash.query()` | 摘要查表后核验原文 | 摘要、字典与列表对象 |
| 建立 LSH | `HyperplaneLSH.__init__()` | 生成超平面、计算编号、按编号排列历史 ID | 建索引投影、排序、桶目录初始化 |
| 读取候选 | `HyperplaneLSH.candidates()` | 定位 L 个桶，拼接 ID 后 `np.unique` | 桶内重复 ID 数量与排序去重 |
| 精筛 | `reuse()` | 仅对 `X[C]` 计算点积 | 候选向量读取与乘加 |
| 真值 | `brute()` | 全部 N 条向量点积 | 仅用于基线与离线评价 |
| 指标 | `summarize()` | 空真值单列，分别汇总 Recall 与候选量 | 避免混淆分母 |
| 计时 | `timings()` | 预热、多轮、轮换方法执行顺序 | 环境噪声、缓存、线程数 |

代码文件见 [experiment.py](验证/experiment.py)。

每张表用两个数组表达所有桶：`offsets` 给出桶的起止位置，`ids` 连续保存按桶排列的历史 ID。编号为 b 的桶内容是：

```python
ids[offsets[b]:offsets[b + 1]]
```

查询时直接读取桶区间，没有遍历全部 N 个编号来找同桶元素。

当前为比较消融而生成一组 `92 × 16 × d` 的独立超平面，再取对应 L 和 k 的前缀。主配置真正持有并使用的是 `46 × 12` 个超平面。相同种子下，不同配置复用前缀，所以我们能观察到固定 L 时增加 k 的候选集合收缩、固定 k 时增加 L 的候选集合扩张。生成大超平面库的临时空间不包含在持久索引内存统计中。

## 8. 怎样读实验指标

### 8.1 Recall 的分母

单个非空查询的 Recall 为：

\[
\mathrm{Recall}(q)=\frac{|A(q)|}{|G(q)|}.
\]

Macro Recall 是各非空查询 Recall 的平均，每个查询权重相同；Micro Recall 是全部找回的相关对数除以全部真实相关对数，邻居多的查询权重更大。

当前 300 个查询中有 273 个非空、27 个空 G。共有 **4,717 对“查询—相关历史文本”**，找回 **4,649 对**，遗漏 68 对，所以 Micro Recall 为 `4649/4717≈98.56%`。Macro Recall 为 98.55%。同一个历史 ID 对不同查询相关，会分别计数，不代表有 4,717 条不同历史文本。

“至少找到一条”的命中率是另一个指标。当前 273 个非空查询全部至少找到一条，但没有保证所有邻居被找齐，也没有保证未见过的查询仍有 100% 命中率。

### 8.2 候选与最终结果不同

Candidate Ratio 是平均 `|C|/N`。主配置每次平均有 790.7 个候选，其中约 775.2 个低于阈值，最终平均返回约 15.5 个。候选中仍有大量无关项，但相比全库 10,003 条已经缩小很多。

27 个空 G 查询仍可能产生候选并花费时间。不能因为最终返回空集，就把候选计算成本记为零。

### 8.3 三种方法的主表

| 方法 | Macro Recall | 平均候选比例 | 平均余弦次数 | 平均检索 ms | P95 ms |
|---|---:|---:|---:|---:|---:|
| Brute-force | 100.00% | 100.00% | 10,003.0 | 1.096 | 2.041 |
| Exact Hash Only | 0.00% | 0.00% | 0.0 | 0.020 | 0.036 |
| Hash + LSH | 98.55% | 7.90% | 790.7 | 0.724 | 1.383 |

主表只用非重复查询，所以 Exact Only 的语义 Recall 为零。这表明只做精确缓存无法完成本任务的第二层需求，不表示精确缓存没有应用价值。100 个重复查询的测试中，两种 Hash 方法均全部命中，且不进行余弦计算。

## 9. 用三个真实查询走一遍

下述索引均从 0 开始，与 [逐查询记录](验证/主实验逐查询.json) 的 `query` 和 [数据划分](数据/划分.json) 的 `semantic_queries` 一致。历史 ID 对应 `history` 数组下标。文本取自 BANKING77，数据许可及来源见 [数据目录](数据/)；保留原始拼写。

### 9.1 查询 0：全部相关项都进入候选

查询原文：`Are there certain ATMs that I can use this card at?`

其中一个相关历史请求为 ID 7873：`Are there specific ATM's I can use with this card?`，余弦约 0.94485。

- Ground Truth 有 23 条。
- LSH 得到 732 个候选。
- 精筛返回 23 条，单查询 Recall 为 100%。

这说明表面措辞不同的请求，可以通过向量相近而进入候选。732 个候选中有 709 个最终被剔除，因此“同桶”远不足以确认相关。

### 9.2 查询 165：有答案，但没有找齐

查询原文：`How many miles away is the ATM?`

| 历史 ID | 历史原文 | 余弦约值 | 是否进入候选 |
|---:|---|---:|---|
| 6032 | How far is the closest ATM from me? | 0.84031 | 是 |
| 3602 | Is the closest ATM to me within 2 miles? | 0.81345 | 否 |

本查询产生 304 个候选，G 有 2 条，最终返回 1 条，Recall 为 50%。这是按当前记录选出的最低单查询 Recall 案例，用于分析漏检，不用来代表全部查询的平均表现。

第二条历史请求虽然达到了 0.80 阈值，却没能在任意一张表与查询同桶。损失发生在候选生成阶段；后面的余弦精筛无法再看到它。下一步可以研究它与查询的桶编号相差几个 bit，以及漏掉的其他相关项是否也更接近阈值。

此外，两条历史问题与查询在回答形式上的差别，提醒我们：阈值邻居不自动意味着历史答案可原样复用。

### 9.3 查询 3：没有阈值邻居，也要付出候选成本

查询原文：`I tryed to make a top-up with cryptocurrency but the payment was referted.`

全库最高余弦约为 0.73083，因此 G 为空。LSH 仍得到 1,184 个候选，精筛后返回 0 条。

这个案例说明：没有相关项不代表 LSH 不会碰撞。当前宏平均 Recall 排除它，但候选比例和查询成本保留它。若后续只挑选有邻居的查询，会把实际负载中的一类成本漏掉。

## 10. 时间与空间成本怎样拆开

### 10.1 为什么余弦减少 12.65 倍，耗时只加快 1.51 倍

主配置的语义查询包含：摘要查找、552 次 d 维投影、46 次桶定位、候选合并去重、候选向量读取、最终余弦精筛。暴力搜索则对连续向量矩阵作一次整齐的运算，底层数值库很擅长处理这种访问模式。

令 B 表示去重前所有桶内 ID 的总数，当前实现的主要查询成本可以写成：

\[
O(|q|+kLd+B\log B+|C|d),
\]

这里没有计入查询 Embedding。`np.unique` 的排序与候选读取都是实际工作，不能把全部查询成本等同于 `|C|` 次点积。B 与 |C| 也不一样：跨表重复越多，去重前工作可能越大。

现有计时在相同预计算向量上、单线程 BLAS 下进行；预热后每查询测 5 轮，轮换方法顺序。主实验记录的是这次运行的耗时，不是固定硬件上的永久常数。逐查询原始计时样本未保存，当前文件只保留汇总统计；后续若要分析延迟与桶密度的关系，需要补充原始计时记录。

### 10.2 空间来自哪里

| 存储部分 | 当前主要字节数 | 学习要点 |
|---|---:|---|
| 历史向量 | 15,364,608 | `N × d × 4`，约 14.65 MiB |
| LSH 超平面 | 847,872 | `L × k × d × 4` |
| LSH 桶偏移 | 753,848 | `L × (2^k+1) × 4`，含空桶目录 |
| LSH 历史 ID | 1,840,552 | `L × N × 4`，每条历史在每张表存一次 |
| LSH 位权数组 | 48 | `k × 4` |
| LSH 数组容器等 | 11,488 | 当前实现统计到的对象开销 |
| Exact 索引 | 2,105,535 | 字典、摘要键、ID 列表和整数对象 |

LSH 数组负载合计约 3.28 MiB。加上容器和 Exact 表，额外索引约 5.30 MiB；与全部向量一起约 19.95 MiB。原文公共存储、模型、解释器以及构建阶段峰值内存另计，所以这些数字不等于整个进程占用的 RSS。

这里同时涉及两个量化概念：模型权重量化不等于检索向量压缩，LSH 编号也没有替代用于精筛的原始向量。当前方案总体上增加存储。

### 10.3 建索引是否值得

当前主配置 LSH 构建计时约 0.234 秒，不含 Exact 建表、模型下载与向量编码。用这一次测得的检索均时差 `1.096−0.724≈0.372 ms` 粗略摊销，仅 LSH 构建成本约需 630 次查询才能抵消。

这是基于当前测量的估算，不是普遍盈亏界；更新频率、重复请求比例、批量查询、实际硬件和缓存状态都会改变它。若历史库建好后只查询几次，即使单次 LSH 较快，也未必值得预先构建索引。

## 11. 已完成的消融与规模实验

### 11.1 每次改变一个主要参数

| k | L | Macro Recall | 候选比例 | LSH 数组 MiB |
|---:|---:|---:|---:|---:|
| 8 | 46 | 99.99% | 39.74% | 2.34 |
| 12 | 23 | 88.22% | 4.25% | 1.64 |
| 12 | 46 | 98.55% | 7.90% | 3.28 |
| 12 | 92 | 99.90% | 15.38% | 6.57 |
| 16 | 46 | 86.28% | 1.66% | 14.33 |

固定 L 比较 k=8、12、16，观察桶条件收紧的代价；固定 k 比较 L=23、46、92，观察增加相遇机会的代价。不要把同时改变 k、L 的两行差异全部归因于其中一个参数。

k=16 虽然候选最少，索引却最大，这是当前密集目录的 `2^k` 项造成的。少算相似度不意味着少用内存，也不意味着总体延迟一定最低。当前消融没有分别保存全部配置的检索计时，不能从此表推断哪个配置实际最快。

主配置另测了三个预定种子，Recall 在 97.89% 至 98.65% 之间，候选比例在 7.90% 至 8.99% 之间。三次结果说明存在随机波动，不能作为严格置信区间，也没有据此替换主表种子。

### 11.2 历史库扩大，候选数如何增长

| N | 平均候选数 | 候选比例 | 平均无关候选 |
|---:|---:|---:|---:|
| 2,000 | 156.3 | 7.82% | 153.3 |
| 5,000 | 394.4 | 7.89% | 386.8 |
| 10,003 | 790.7 | 7.90% | 775.2 |

使用同一组超平面、同一批查询和嵌套的随机历史子集；每个规模重新计算 G。这里观察的是相似度分布近似稳定时的增长，不包含新增领域造成的分布变化。

对固定查询，用指示变量的期望相加可得：

\[
\mathbb{E}|C(q)|=\sum_{i=1}^{N}P(\mathrm{sim}(q,x_i)).
\]

这个期望求和不需要假设不同历史元素的碰撞事件相互独立。若分布稳定、单元素平均进入概率维持正常数，候选比例可近似稳定，而绝对数量随 N 线性增长。

假设无关项进入概率为 α=0.001，且有 10^8 个此类元素，期望仍是 10^5 个无关候选。这是理论数量级示例，不是本次在一亿条数据上的实测。

只增大 k 会损失近点召回；为维持召回又增加 L，则投影与存储会增长。大规模设计需要联合考虑这些项，不能把“候选比例低”当作可无限扩展的证据。

## 12. 当前证据支持什么，还有什么没有回答

| 问题 | 当前证据 | 尚不能推出的结论 |
|---|---|---|
| LSH 是否少检查历史 | 平均检查 7.90%，完整候选 ID 可核对 | 每个查询都只检查 7.90% |
| 是否保持较高相关项覆盖 | Macro 98.55%，Micro 98.56% | 每个查询都达到约 98%，或答案正确率为 98% |
| 是否更快 | 当前检索均时约快 1.51 倍 | 包含 Embedding 和生成的系统也快 1.51 倍 |

## 13. 后续怎样改进，先做什么

本节全部为**待验证方向**，本次只记录方案，不改算法、不重新选参数。

| 优先级与实验编号 | 要回答的问题 | 单次主要改动或新增观测 | 应比较的指标 | 可能代价 |
|---|---|---|---|---|
| 第一轮 E01 | 为什么少数相关项没有进入候选？ | 给当前漏检项记录余弦、各表 Hamming 距离、边界投影绝对值 | 漏检的相似度分布、最近桶距离；完整样本对照 | 分析成本，不应改变原始召回 |
| 第一轮 E02 | 真实查询成本花在哪里？ | 保存分阶段与逐查询计时，同时记录 B、\|C\|、重复比例和桶大小 | 投影、查桶、去重、精筛均时及 P95 | 插桩自身会影响计时，应与未插桩总耗时对照 |
| 第二轮 E03 | 较大 k 的目录能否省空间？ | 将密集桶目录替换为仅保存非空桶的结构 | 索引字节、构建成本、查询时间，候选集合逐项一致性 | Python 字典开销及查找局部性可能抵消收益 |
| 第二轮 E04 | 少量额外探桶能否减少表数？ | 多探测：在原桶外探测少量翻转 bit 的邻桶，固定探测预算 | Recall、候选比例、实际桶访问数、延迟和空间 | 更多查桶、候选与去重；原始单桶公式不能直接套用 |
| 第三轮 E05 | 最小可行 k 是否对应最快配置？ | 在开发集按时间与内存预算联合选择 k、L | 达到目标 Recall 后的延迟、P95、索引内存 | 容易过拟合开发集，需新的独立测试 |
| 第三轮 E06 | 原文缓存是否可以更简单？ | 对比 SHA-256 映射与直接字符串字典 | 相同正确性下的命中/未命中耗时和索引空间 | 结果依赖语言运行时和文本长度 |
| 第四轮 E07 | 高余弦能否代表答案可复用？ | 为一批匹配对增加人工判定和条件检查 | 人工相关性、可复用精度、错误复用类型 | 改变研究层次，需要标注，不再只有向量真值 |

建议先完成 E01、E02，再决定采用何种索引改进。若瓶颈主要在投影，单纯优化去重的收益可能有限；若热点桶占据大部分候选，应优先理解数据密度。每次实验应有一个可以被结果否定的假设，而不只是“尝试某个新方法”。

E03 属于实现替换，理想上 C 和 A 完全不变，只改变开销；E04 会改变候选集合，是算法策略变化；E07 则改变评价目标。这三类实验需要不同的验收标准。

## 14. 后续实验的约束与记录模板

### 14.1 保留当前基线，避免覆盖和测试集泄漏

当前脚本将结果写入固定文件名，重新运行 `experiment.py` 会覆盖主实验结果和逐查询记录。开始改进实验前，应先支持独立输出目录，或保存一份完整基线快照，再把新运行写入例如 `实验迭代/E01_漏检分析/` 的目录。本轮文档工作没有执行新检索实验，也没有覆盖原结果。

快照应包含方案、源码、数据划分、模型来源、向量校验、结果与审计文件，并记录对应 SHA-256。只保留一个汇总数字不足以还原实验。

当前 300 个查询的结果已经看过。后续据其结果提出改动后，它们可以继续作为回归比较集，但不能再宣称是从未接触过的最终测试集。需要调参时，应明确开发集，并从尚未用于本次分析的测试文本中预留新的最终评价集，先固定划分与目标，再运行评价。

同时遵循：

- 比较 k、L 或桶结构时，保持模型、向量、τ、历史库和查询不变。
- 若修改 τ 或模型，要重新计算 G，并承认相关性任务随之改变。
- 新阈值下的 Recall 不能与旧阈值 Recall 脱离 G 的大小直接比较。
- 改参数时说明哪些随机数复用、哪些重新采样；不只报告最好种子。
- 空 G 查询保留在成本统计中；Exact 与非重复查询分组报告。
- 候选截断、提前停止、二级过滤都可能新增漏检，必须单独量化。
- 若由“找齐阈值邻居”改为“找到一条即可”，应另立返回约定与指标。
